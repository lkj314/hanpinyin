## 1. 本轮审计结论（新增，全部有实证）

### 1.1 单词条学习 = 真实有效 ✅

- **机制**（源码）：每次选词上屏 → userdb 记一条 `码\t词 => c=提交次数 d=权重 t=时间戳`，同码重输时学过的词参与排序且按「频次 × 新近度」计权，久不用会衰减。
- **实验**（隔离环境，6 次提交）：故意选第二候选 어떡해요，重输 `zmb` 后它**跳到首位**——"记住喜好"成立。
- **真实数据**（你的 userdb，54 条）：`hah`→ㅋㅋ c=7、`wanan`→잘자 c=6、`lihao`→안녕하세요 c=5、`wandangle`→망했다 c=5、`dabuguole`→못 이겨 c=4……学习正常积累中。
- **两个细节**（实验发现，值得知道）：
  - 学习按 **(码, 词) 对**生效：在 `zmb` 下学了 어떡해요，敲 `zenmeban` 不继承这个偏好；
  - **模糊派生码会原样入库**：敲 `nihao` 可能被记成 `lihao \t안녕하세요`（speller algebra 派生码参与匹配）。无害，但挖矿统计时要按词聚合而不是按码。

### 1.2 ☯ 长句自学习 = 两层断裂，判定不可修 ❌（T1-1 归因完结）

- **断裂①（生产现症）**：编码器开关在**词典 settings** 而非 schema——真实词典缺 `encoder:` 段，librime `unity_table_encoder.cc:39` 报 "unity table encoder is not enabled in dict settings"，schema 里的 `enable_encoder/encode_commit_history: true` 形同虚设（实验 E1 用真实 schema+词典隔离编译复现）。
- **断裂②（librime 内部）**：给词典补上 `encoder.rules` 后警告消失，但生产形态下 6 连击提交后 WAL 仍零 `\x7fenc` 条目、重开引擎探针全空（实验 E4）——编码器拆词环节对多音节连写韩文词典不工作，无编译器不可修。
- **旁证**：`enable_sentence` 的 ☯ 候选是**临时组句**（不落库、会话即逝），不是自学习（实验 E3）。
- 完整归因、实验记录与源码引证见 **`docs/SELF-LEARNING-MEMO.md`**。

### 1.3 使用状态 = 学习引擎在空转 ⚠️

- userdb 最后写入时间 **2026-09-26 05:11**（部署当日），此后一个月零提交。十月要么没用 HanPinyin，要么只用它看候选没上屏。
- 含义：所有"越用越顺"的前提是**真的用它打字**。学习侧机制已就绪（1.1），缺的是使用侧数据。

### 1.4 学习数据污染 ⚠️（小）

- `shengqi \t生气`（中文）混入了 userdb——v2.4 之前旧词典时代选中的残留。由于用户词在同码下有优先权，敲 `shengqi` 时**生气会排在 빡쳐 系列前面**。
- 另有条目 `gg \t오빠`、`ln \t쉬바나` 等疑似旧词典时代的历史产物，韩文无害，仅记录。
- librime 无单条删除 API；可选处置见 T1-5。

## 3. 已否决事项清单（勿重提）

| 事项 | 否决原因 |
|---|---|
| 复活 `src/` 自研 TSF | 死刑存档，铁律 4 |
| CLI/脚本自动部署 | 系统级软件脚本改不动也验不了，铁律 1 |

| 全局权重分级 / initial_quality 调优 | 权重只在同码内比较；exp(权重) 面前可忽略 |
| 重新开启前缀补全 | 实测噪声源（补全 -1 压不住 e^12） |
| 恢复中文候选 | 分工已定：中文=搜狗 |
| 依赖 ☯ 长句编码作为长句流畅度方案 | **本轮实证：从未产出**；改为 T1-1/T1-2 重新评估或走固化路线 |
| 要求用户预先列出缺词/排序清单 | 用户明确否决（2026-10-31）：改为 userdb 挖矿数据驱动 + 零负担随手记 |

## 4. 铁律（全程有效，同前版）

1. 禁止命令行自动化改动输入法/触发部署；build/verify/bench/mine 等纯数据脚本豁免。
2. 先查 Rime/Weasel 官方源码，不猜机制。
3. 验证 = 手动打字测试。
4. 不碰 `src/`。
5. Git：显式 add、禁 `git rm -r`、SSH push 后 `git ls-remote` 核实。
