# HanPinyin 产品需求文档（简单 PRD）

> 文档类型：简单 PRD（仅产品需求侧，不含架构/代码）
> 项目代号：HanPinyin —— 基于汉语拼音的韩语输入法（韩服专用）
> 版本：v0.1（初稿）
> 作者：许清楚（Product Manager）

---

## 1. 产品目标

HanPinyin 是一款面向韩服《英雄联盟》等游戏的中国玩家、基于汉语拼音的轻量级韩语输入工具，旨在通过用户熟悉的拼音输入实时转换为韩语文本并快速发送至游戏窗口，消除韩语键盘布局（두벌식）带来的沟通障碍，让不熟悉韩文键位、但有拼音基础的玩家也能零学习成本地与队友交流。

---

## 2. 用户故事

| 编号 | 用户故事 |
|------|----------|
| US-1 | 作为韩服 LOL 玩家，我希望直接输入拼音即可打出韩语，以免记忆韩文键位与映射规则。 |
| US-2 | 作为不熟悉韩语的中国玩家，我希望连续输入整句拼音能自动得到韩语句子，以便快速与队友沟通战术。 |
| US-3 | 作为游戏玩家，我希望选中韩语后能一键发送到当前游戏窗口，以免切换输入法打断操作节奏。 |
| US-4 | 作为长期使用玩家，我希望输入法记住我常用的词并优先展示，以便后续输入更快更准确。 |
| US-5 | 作为南方口音玩家，我希望模糊拼音（如 zh/z）也能被正确识别，以免打不出想要的词。 |

## 3. 需求池（优先级映射）

优先级定义：
- **P0（必须有）**：缺失则产品核心不可用，阻塞上线。
- **P1（应该有）**：显著提升体验，可在首个可用版本后尽快补充。
- **P2（可以有）**：锦上添花，MVP 可不包含。

### 3.1 功能需求

| 编号 | 需求 | 优先级 | 判定理由 |
|------|------|--------|----------|
| F1 | 拼音→韩语转换（完整拼音或首字母缩写输入，输出韩语） | **P0** | 产品核心价值，无此功能则产品不成立。 |
| F2 | 多候选词（数字键选择，同音多词展示列表） | **P0** | 拼音→韩语的映射天然一对多，无候选则无法选对词，核心体验缺失。 |
| F3 | 模糊拼音（zh/z、ch/c、sh/s、an/ang 等） | **P1** | 提升口音用户命中率，但多数用户无此需求，可后置并默认开关。 |
| F4 | 整句输入（连续拼音串自动分词并匹配最佳组合） | **P0** | "整句拼音→整句韩语"是区别于普通输入法的核心卖点（见 US-2）。 |
| F5 | 常用短语库（预置约 200 条韩服游戏常用语） | **P1** | 明显提升开局体验，但词条可后续累积，不阻塞首版可用。 |
| F6 | 用户词库（记录历史选择，优先高频词） | **P1** | 越用越准，但首版无词库也能工作，属体验增强。 |
| F7 | 快捷发送（选中后模拟 Ctrl+V / SendInput 发至激活窗口） | **P0** | 在游戏场景若不自动发送，工具无法落地使用，是闭环关键。 |
| F8 | 悬浮窗 UI（跟随光标小窗，鼠标点击或数字键选择） | **P0** | 唯一交互载体，无 UI 则用户无法选择/发送，必备。 |

### 3.2 非功能需求

| 编号 | 需求 | 优先级 | 判定理由 |
|------|------|--------|----------|
| NF-1 | 响应速度：输入完成到显示候选 < 50ms（本地词典，无网络依赖） | **P0** | "轻量、实时"是核心承诺；卡顿将直接破坏游戏内沟通。 |
| NF-2 | 内存占用：< 20MB（含词库） | **P1** | 重要但非上线阻塞项，可后续优化，MVP 略超亦可接受。 |
| NF-3 | 兼容性：Windows 10/11，支持 DirectInput 游戏窗口 | **P0** | 目标场景即游戏内输入，若无法在游戏窗口生效则产品失效。 |
| NF-4 | 可扩展：词库 JSON 或 SQLite，用户可自行增删 | **P2** | 利于长期维护，但 MVP 可先固定内置词库，后续开放编辑。 |

> 说明：用户原始方案将"可扩展性"也列入非功能需求，故此处实际为 4 条非功能项（NF-1~NF-4）；其优先级按对首版上线的阻塞程度判定。

## 4. UI 设计稿（主悬浮窗布局）

### 4.1 布局示意（ASCII）

```
┌────────────────────────────────────────────┐  ← 主悬浮条 300×30（半透明，无边框）
│ 🔤 wan le yi xia wu            [输入中]      │
└────────────────────────────────────────────┘
            │（跟随光标/输入光标下方展开）
            ▼
┌────────────────────────────────────────────┐  ← 候选区（最多显示 5 条）
│ 1. 오후 내내 했어   (wan le yi xia wu)        │  ← 鼠标悬停高亮
│ 2. 완료             (wan le)                  │
│ 3. 완료됐어         (wan le)                  │
│ 4. 왠일이야         (wan le)                  │
│ 5. …                (更多 → Tab 翻页)         │
├────────────────────────────────────────────┤
│ 数字键 1~5 选择 · Tab 翻页 · 鼠标点击          │
│ Esc 取消 · Enter 直接发送首个候选              │
└────────────────────────────────────────────┘
```

### 4.2 状态指示与交互说明

| 元素 | 说明 |
|------|------|
| 状态图标 🔤 | 输入法激活（拦截字母/数字键，进入输入模式）。 |
| 状态图标 🈳 | 输入法关闭（按键全部透传，不拦截）。 |
| 拼音输入行 | 实时显示已输入的拼音串；空格确认当前串并开始匹配，退格删除最后一个音节。 |
| 候选项格式 | `编号. 韩语 (拼音原文)`，按词频降序排列。 |
| 数字键 1~5 | 选择对应候选词并发送。 |
| 鼠标 | 悬停高亮，点击直接选择并发送。 |
| Tab | 候选超过 5 条时翻页。 |
| Esc | 取消当前输入，清空候选，回到透传状态。 |
| Enter | 直接发送首个候选（最快路径）。 |
| 热键 Ctrl+Space | 切换输入法激活/关闭状态。 |

## 5. 待确认问题（需主理人 / 用户澄清）

1. **首字母缩写匹配规则**：F1 提到支持"首字母缩写"但未定义（如 `wl` 是否映射到 `wan le`、`wlyxw` 映射逻辑）。需明确缩写解析规则、最大缩写长度，以及缩写与完整拼音冲突时的歧义处理策略。
2. **模糊音完整映射表与默认开关**：F3 仅列举 zh/z、ch/c、sh/s、an/ang。是否需补充 n/l、r/l、前后鼻音（in/ing、en/eng）等？模糊音默认开启还是需用户手动开启？需提供最终映射表。
3. **Direct2D 是否可降级为 GDI**：为降低实现复杂度与系统依赖，MVP 是否可用 GDI/GDI+ 渲染悬浮窗（外观/性能底线是否可接受），后续再升级 Direct2D？需主理人确认渲染技术底线。
4. **词库初始规模与来源**：F5 预置约 200 条短语；主词库 `PinyinEntry` 与 `phrases.json` 的首版词条数量、韩语标注质量由谁提供（产品提供词表 vs 工程自采）？需明确初始数据交付方与时间。
5. **是否需要图形配置界面**：用户增删词库（F5/F6 可扩展）、开关模糊音、自定义热键等，是否需要图形配置面板，还是首版先支持手改 JSON/SQLite 即可？
